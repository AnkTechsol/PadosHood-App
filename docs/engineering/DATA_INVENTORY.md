# Data inventory — launch scope

This inventory describes observed/intended application fields only. It is not a retention policy or legal compliance statement. Retention period, database hosting location, legal operator, and provider transfer locations are not established; see [retention schedule](DATA_RETENTION_SCHEDULE.md) and [legal review](../legal/LEGAL_REVIEW_REQUIRED.md).

| Data | Source and purpose | App storage/access | Service involved | Export/deletion behavior |
|---|---|---|---|---|
| Name, block/tower, flat, Owner/Tenant | Entered by resident for joining, identification within this fixed society, and complaint location context | PostgreSQL `ang_members`; the resident and authorized committee administrators have scoped use | Application server/PostgreSQL; Clerk user ID associates the membership with the authenticated identity | Signed-in applicants/members, including Pending, Rejected, and Suspended status, can expand Account and access export/delete controls. Own export includes member record. Deleting application account removes membership; it does not delete Clerk identity |
| Clerk user ID | Provider identity used to locate membership and audit actor | PostgreSQL membership/audit records; server-side only | Clerk and application server/database | Membership deletion removes member ID; audit rows may retain actor ID for administrative actions. Provider-side identity deletion is a separate Clerk/operator request |
| Notice title/content/priority | Committee-authored society communications | PostgreSQL `ang_notices`; approved members read; admins create/edit/delete | Application server/PostgreSQL | Notices are society records, not included in resident own-data export or deleted with a resident account |
| Discussion post text | Resident-authored community discussion | PostgreSQL `ang_posts`; approved members read; author edits; admins moderate | Application server/PostgreSQL | Own export includes own posts; account deletion cascades own posts |
| Complaint title, description, category, priority, status, generated block/flat location, timeline status/note | Resident-submitted text for maintenance/reporting and committee handling | PostgreSQL `ang_complaints` / `ang_complaint_events`; resident sees own complaints, approved admin sees all | Application server/PostgreSQL | Own export includes own complaints and timeline; account deletion cascades complaints and timeline events |
| Audit metadata (actor ID, action, target type/ID, timestamp) | Generated by sensitive admin operations for accountability; no content body | PostgreSQL `ang_audit`; server/operators with database access | Application server/PostgreSQL | Current schema has no deletion/expiry schedule; owner must approve policy. Account deletion does not guarantee removal of historical audit metadata |

The server request logger/audit calls must not record submitted content, session tokens, credentials, or other unnecessary personal data. Actual platform/access logs and Clerk data processing are subject to provider configuration and must be confirmed with the deployment/operator before release.

Not collected in the launch API/schema: resident phone/email fields (Clerk may process account credentials under its own service), health/blood-group data, visitor details, payment data, attachments/documents/images, location tracking, ratings, AI prompts, or approved analytics events. Do not infer that legacy/demo records have reliable provenance.
